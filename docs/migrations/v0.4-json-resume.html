Migrating to the JSON Resume structure in v0.4 ​

Web Resume v0.4 adopts the JSON Resume field structure for new and converted documents. Existing YAML remains supported during the v0.4 migration period.

Delivered in v0.4 ​

  • The canonical JSON Resume schema is pinned, with standard, legacy, and combined editor schemas published by the app.
  • Both formats are detected and validated against their own contracts.
  • Canonical documents render through an isolated adapter.
  • Editor conversion is explicit, reviewable, and undoable.
  • The CLI supports read-only checks and conversion to a separate output file.
  • Visual drag order is persisted in x-web-resume.sectionOrder for standard documents.
  • Portable export strips extensions and non-standard fields before canonical validation and download.
  • Built-in presets use the standard structure, with mixed employment, project, volunteer, award, and publication entries resolved by meaning.
  • The remaining canonical sections—volunteer, publications, languages, interests, and references—are rendered.
  • The target stable data contract is documented for the eventual v1.0 release.

Compatibility policy ​

  • Existing legacy YAML continues to load and render without being rewritten.
  • The editor detects legacy documents and offers an explicit conversion review.
  • Conversion only writes to the editor after confirmation and can be undone with the editor's normal undo command.
  • New standard documents may remain YAML; JSON Resume defines the data shape, not the authoring syntax used by Web Resume.
  • Presentation-only data is stored under the single x-web-resume extension.

Editor conversion ​

Open a legacy document in the editor and choose Review and convert. The review lists fields that need attention. Confirming replaces the editor content but does not alter the originally loaded URL or file. Use Undo immediately to restore the previous text.

The converter does not silently guess when:

  • a legacy project is actually employment;
  • an entry under certificate is an award, certificate, or publication;
  • a free-form location cannot be split into structured address fields;
  • a localized or ranged date cannot be represented as YYYY, YYYY-MM, or YYYY-MM-DD.

Values that cannot be represented safely are retained in x-web-resume and reported as warnings. YAML comments are reported separately because the current conversion serializer cannot preserve them.

Unknown fields are retained under x-web-resume.legacyFields. Each key is the field's original JSON Pointer path, so custom data remains recoverable without duplicating the complete legacy document.

CLI conversion ​

Check a file without writing:

bash
pnpm migrate:resume -- --input ./resume.yml --check

The check exits successfully for a valid standard document and with status 1 when a legacy document needs migration or validation fails.

Write a converted copy:

bash
pnpm migrate:resume -- --input ./resume.yml --output ./resume.v0.4.yml

The CLI never overwrites the input implicitly. Review the warnings and diff before replacing the original file.

Schema URLs ​

  • /schema/resume.schema.json: combined editor schema accepting standard and legacy documents during v0.4.
  • /schema/json-resume.schema.json: the pinned canonical JSON Resume schema bundled with the app.
  • /schema/resume-legacy.schema.json: the previous Web Resume data contract.

Rollback ​

Before conversion, keep the source file or commit it to version control. In the browser, conversion is a single undoable editor operation. For CLI conversion, the input remains untouched unless you replace it yourself.

Legacy reading will not be removed during v0.4. Any future removal must be announced as part of the stable 1.0.0 data contract and include a tested migration path.

The target stable contract is documented in Data contract for v1.
